3. Por que SQL e NoSQL importam?

Aplicações transacionais

ERPs, CRMs, e-commerce, billing, folha e sistemas financeiros precisam de consistência, integridade e controle transacional.

Aplicações orientadas a conteúdo

Catálogos, documentos, logs, eventos, telemetria e sessões exigem flexibilidade de esquema e escalabilidade horizontal.

Aplicações de IA

LLMs, agentes inteligentes, RAG, busca vetorial e automação dependem de dados bem organizados, metadados, índices e governança.

Nenhum banco resolve tudo sozinho. O mercado evoluiu para a ideia de arquitetura de dados combinada: relacional para transações críticas, NoSQL para escala e flexibilidade, e mecanismos especializados para busca, analytics e IA.

5. Ecossistema atual de dados

Camada operacional

Sistemas de registro usam SQL para pedidos, pagamentos, cadastros, contratos e dados mestres. Prioridade: ACID, segurança e auditoria.

Camada de experiência

Sites, apps, catálogos, documentos, chat, telemetria e cache usam NoSQL para obter desempenho, elasticidade e menor atrito de modelagem.

Camada analítica

Data warehouses e lakehouses consolidam históricos, métricas, fatos e dimensões para BI, planejamento e modelos analíticos.

Camada de IA

Busca vetorial, grafos, feature stores, catálogos e metadados ajudam a construir RAG, recomendação, agentes e automação inteligente.

6. Conceitos essenciais

Banco de dados

Coleção organizada de dados persistidos para suportar aplicações e decisões.

SGBD

Software que cria, consulta, atualiza, protege e recupera os dados.

Esquema

Estrutura lógica: tabelas, coleções, tipos, índices, relacionamentos e regras.

Índice

Estrutura auxiliar que acelera buscas ao custo de espaço e manutenção.

Transação

Unidade de trabalho com início, confirmação (commit) ou cancelamento (rollback).

Sharding

Distribuição dos dados em múltiplos nós para escalar horizontalmente.

Replicação

Cópia dos dados entre nós para disponibilidade e leitura distribuída.

Latência

Tempo para executar uma operação. Em aplicações digitais, poucos milissegundos importam.

7. ACID, BASE e CAP

ACID

  • Atomicidade: tudo ou nada
  • Consistência: regras preservadas
  • Isolamento: concorrência controlada
  • Durabilidade: persistência após commit

BASE

  • Basic Availability
  • Soft state
  • Eventual consistency
  • Mais comum em sistemas distribuídos orientados a escala

Leitura prática: bancos distribuídos geralmente precisam balancear consistência, disponibilidade e tolerância a partições. A escolha depende do risco de inconsistência versus a necessidade de resposta contínua.

9. SQL e NoSQL em uma frase

SQL

Ideal quando os dados têm estrutura relativamente estável, exigem integridade forte, consultas relacionais ricas e linguagem padronizada.

NoSQL

Ideal quando há necessidade de alta elasticidade, grande volume, baixa latência, modelos flexíveis ou um tipo de dado muito específico.

O ponto decisivo não é “moda”, mas sim aderência da tecnologia ao problema.

11. Normalização

1FN

Elimina grupos repetidos e garante valores atômicos em cada coluna.

2FN

Remove dependências parciais em chaves compostas.

3FN

Remove dependências transitivas para reduzir redundância e anomalias.

Na prática, normalizar ajuda a manter a qualidade, mas alguns cenários de leitura analítica ou alta performance usam desnormalização consciente para reduzir joins e acelerar consultas.

Equilíbrio é a palavra-chave: normalize para manter integridade; desnormalize quando houver benefício comprovado para leitura ou distribuição.

12. Exemplo prático: loja virtual

Leitura: o cliente realiza muitos pedidos; um pedido possui muitos itens; cada item referencia um produto. Esse desenho é a base para criar tabelas, chaves e índices.

20. Transações, concorrência e isolamento

Fluxo transacional

BEGIN → operações → COMMIT ou ROLLBACK. Em casos críticos, o banco deve garantir consistência mesmo diante de falhas.

Níveis de isolamento

Read Uncommitted, Read Committed, Repeatable Read e Serializable controlam fenômenos como dirty reads, non-repeatable reads e phantom reads.

ComandoUso
BEGIN / START TRANSACTIONinicia a transação
COMMITconfirma alterações
ROLLBACKdesfaz alterações
LOCK / SELECT ... FOR UPDATEprotege leitura e escrita concorrente

50. Passo a passo genérico de modelagem

EtapaO que fazer
1. Entender o problemaMapear objetivos de negócio, eventos, consultas, integrações, SLA e riscos.
2. Identificar entidades/dadosDefinir entidades, atributos, relacionamentos, documentos, chaves e cardinalidades.
3. Projetar consultasComeçar pelas perguntas que o sistema precisa responder; isso direciona índices e partições.
4. Escolher a tecnologiaConfrontar latência, consistência, volume, elasticidade e custo.
5. Registrar regrasDocumentar constraints, retenção, LGPD, qualidade, segurança e políticas de acesso.

51. Passo a passo genérico de criação

Infraestrutura

Escolher serviço gerenciado ou autogerenciado; definir rede, ambientes, sizing inicial, backups, monitoramento e automação IaC.

Objeto lógico

Criar databases, schemas, tabelas, coleções, buckets, índices, usuários, roles e chaves de criptografia.

Carga inicial

Popular dados mestres, importar históricos, validar integridade e realizar testes de carga e concorrência.

Operação

Implantar observabilidade, alertas, runbooks, governança, rotinas de manutenção e testes de restauração.
