12. Normalização do modelo

1FN

Cada campo contém valor atômico; produtos do pedido ficam em tabela própria.

2FN

A tabela ItemPedido representa a associação e evita dependências parciais.

3FN

Categoria é separada de Produto; dados do cliente não são repetidos em Pedido.

Resultado: menor redundância, atualização consistente e regras claras de integridade.

18. DDL da tabela produtos

CREATE TABLE produtos (
  id SERIAL PRIMARY KEY,
  nome VARCHAR(140) NOT NULL,
  descricao TEXT,
  preco NUMERIC(10,2) NOT NULL CHECK (preco >= 0),
  estoque INTEGER NOT NULL DEFAULT 0 CHECK (estoque >= 0),
  categoria_id INTEGER NOT NULL REFERENCES categorias(id)
);

19. DDL de pedidos e itens

CREATE TABLE pedidos (
  id SERIAL PRIMARY KEY,
  status VARCHAR(30) NOT NULL DEFAULT 'CRIADO',
  total NUMERIC(10,2) NOT NULL DEFAULT 0,
  cliente_id INTEGER NOT NULL REFERENCES clientes(id),
  criado_em TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE itens_pedido (
  id SERIAL PRIMARY KEY,
  quantidade INTEGER NOT NULL CHECK (quantidade > 0),
  preco_unitario NUMERIC(10,2) NOT NULL,
  pedido_id INTEGER NOT NULL REFERENCES pedidos(id) ON DELETE CASCADE,
  produto_id INTEGER NOT NULL REFERENCES produtos(id)
);

FROM produtos p
JOIN categorias c ON c.id = p.categoria_id
WHERE p.estoque > 0
ORDER BY p.nome;

SELECT cliente_id, COUNT(*) AS pedidos, SUM(total) AS valor_total
FROM pedidos
GROUP BY cliente_id;

27. Mapeamento ORM: Cliente

class Cliente(db.Model):
    __tablename__ = "clientes"
    id = db.Column(db.Integer, primary_key=True)
    nome = db.Column(db.String(120), nullable=False)
    email = db.Column(db.String(160), unique=True, nullable=False, index=True)
    senha_hash = db.Column(db.String(255), nullable=False)
    pedidos = db.relationship("Pedido", back_populates="cliente")

28. Mapeamento ORM: Produto

class Produto(db.Model):
    __tablename__ = "produtos"
    id = db.Column(db.Integer, primary_key=True)
    nome = db.Column(db.String(140), nullable=False, index=True)
    descricao = db.Column(db.Text)
    preco = db.Column(db.Numeric(10, 2), nullable=False)
    estoque = db.Column(db.Integer, nullable=False, default=0)
    categoria_id = db.Column(db.Integer, db.ForeignKey("categorias.id"), nullable=False)

29. Mapeamento ORM: Pedido e ItemPedido

class Pedido(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    status = db.Column(db.String(30), nullable=False, default="CRIADO")
    total = db.Column(db.Numeric(10, 2), nullable=False, default=0)
    cliente_id = db.Column(db.Integer, db.ForeignKey("clientes.id"), nullable=False)
    itens = db.relationship("ItemPedido", cascade="all, delete-orphan")

class ItemPedido(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    quantidade = db.Column(db.Integer, nullable=False)
    preco_unitario = db.Column(db.Numeric(10, 2), nullable=False)
    pedido_id = db.Column(db.Integer, db.ForeignKey("pedidos.id"), nullable=False)
    produto_id = db.Column(db.Integer, db.ForeignKey("produtos.id"), nullable=False)

30. Rota Python: catálogo

@app.route("/")
def catalogo():
    produtos = db.session.scalars(
        select(Produto).order_by(Produto.nome)
    ).all()
    return render_template("catalogo.html", produtos=produtos)
Fluxo: navegador solicita / → Flask executa a rota → SQLAlchemy gera SELECT → PostgreSQL devolve linhas → template monta o HTML.

32. Carrinho na sessão

carrinho = session.get("carrinho", {})
carrinho[str(produto_id)] = carrinho.get(str(produto_id), 0) + 1
session["carrinho"] = carrinho
Nesta versão didática, o carrinho é temporário. Em uma versão avançada, ele poderia ser persistido no banco ou em Redis.

33. Checkout transacional

try:
    pedido = Pedido(cliente=cliente, status="CRIADO")
    db.session.add(pedido)
    for produto_id, quantidade in carrinho.items():
        produto = db.session.get(Produto, int(produto_id))
        if produto.estoque < quantidade:
            raise ValueError("Estoque insuficiente")
        produto.estoque -= quantidade
        db.session.add(ItemPedido(
            pedido=pedido, produto=produto,
            quantidade=quantidade, preco_unitario=produto.preco
        ))
    db.session.commit()
except Exception:
    db.session.rollback()

34. Por que o checkout precisa de transação?

Atomicidade

Pedido, itens e redução de estoque devem ocorrer juntos.

Consistência

Não pode haver pedido sem itens nem estoque abaixo de zero.

Isolamento

Compras concorrentes não devem vender o mesmo estoque indevidamente.

Durabilidade

Após commit, o pedido permanece registrado mesmo com reinício.

52. Desafios de extensão — evolução do MVP

Escolha pelo menos um desafio para transformar o MVP em uma aplicação mais próxima de um e-commerce real. Cada extensão deve gerar alteração no modelo, no código e nas evidências de teste.

NívelDesafioAlterações no bancoAlterações na aplicaçãoEvidência esperada
1 Cadastro administrativo de produtos e categorias
Permitir inclusão, edição, ativação e desativação.		 Adicionar campos como ativo, sku e atualizado_em; criar UNIQUE para SKU e índices de pesquisa. Criar formulários e rotas CRUD; validar preço, estoque e categoria antes de gravar. Cadastro completo + consulta SQL comprovando integridade e ausência de duplicidade.
2 Autenticação e histórico do cliente
Login, logout e área “Meus pedidos”.		 Usar senha_hash; adicionar campos de status/data; garantir e-mail único. Criar sessão autenticada, proteção de rotas e consulta dos pedidos do usuário logado. Login válido/inválido + histórico filtrado pelo cliente correto.
3 Ciclo de vida do pedido
CRIADO → PAGO → SEPARAÇÃO → ENVIADO → ENTREGUE/CANCELADO.		 Validar status; opcionalmente criar tabela historico_status_pedido com data e responsável. Criar painel administrativo para atualização controlada e exibição da linha do tempo. Pedido alterando status com histórico auditável e consulta SQL cronológica.
4 Migrations e testes automatizados
Evoluir o schema sem recriar o banco.		 Adotar Alembic/Flask-Migrate e gerar versões incrementais do schema. Criar testes de catálogo, carrinho, checkout, rollback e regras de estoque. Migration executada + suíte de testes com resultados documentados.
5 Imagens em object storage
Separar arquivos binários do banco relacional.		 Armazenar somente URL, metadados, hash e associação ao produto. Upload controlado, validação de tipo/tamanho e renderização das imagens no catálogo. Produto com imagem externa funcionando sem BLOB no PostgreSQL.
6 Analytics de vendas
Indicadores de receita, ticket médio, produtos e clientes.		 Criar consultas com GROUP BY, CTEs, views e, se necessário, índices por data/status. Construir painel com filtros por período e gráficos de desempenho. Dashboard + SQL utilizado + explicação do plano de consulta e dos índices.
Regra didática: toda extensão deve responder a quatro perguntas: qual problema resolve? o que muda no modelo? o que muda no código? como será testada?

Do requisito ao e-commerce publicado

1. Requisitos

Comece pelo fluxo do negócio. Catálogo, carrinho, checkout, estoque e cliente definem quais dados precisam existir.

2. Modelagem

Transforme o domínio em entidades, atributos, cardinalidades, chaves e regras. Modele antes de codificar.

3. Integridade

Use PK, FK, UNIQUE, NOT NULL e CHECK para impedir que estados inválidos cheguem ao banco.

4. PostgreSQL

O SGBD open source fornece SQL, ACID, índices, constraints e portabilidade entre ambiente local e cloud.

5. Python + ORM

Flask recebe a requisição; SQLAlchemy mapeia objetos para tabelas; psycopg realiza a comunicação com PostgreSQL.

6. Transações

No checkout, pedido, itens e estoque formam uma unidade. Use commit somente quando tudo estiver consistente; caso contrário, rollback.

7. Testes

Teste o fluxo feliz e as exceções: item inexistente, estoque insuficiente, conexão indisponível e entradas inválidas.

8. Cloud

Separe código e segredos, use variáveis de ambiente, conexão segura, logs sem credenciais e banco com backup.

Dicas essenciais para o projeto

  • Modele a partir das consultas e regras do negócio, não apenas a partir das telas.
  • Preço monetário: prefira NUMERIC/DECIMAL, não FLOAT.
  • Índice deve ter propósito: meça consultas antes e depois da criação.
  • Não grave senha nem conexão no código. Use hash e variáveis de ambiente.
  • Faça rollback em falhas transacionais e teste concorrência quando houver estoque.
  • Versione o schema com migrations à medida que o projeto evoluir.
  • Teste restauração e não somente backup.
  • Documente decisões: requisito → modelo → SQL → código → teste → deploy.
A ideia central: o banco de dados não é um componente isolado. Ele participa de todo o ciclo de desenvolvimento, da regra de negócio à operação em produção.
